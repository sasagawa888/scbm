
# SCBM-Prolog TODO：再帰失敗時のバックトラックと成功継続の温存

## 問題の発見

`perm1([1,2,3], X)` のバックトラックを詳細に追跡したところ、計算そのものはかなり正しく進んでいる。

特に先頭を `2` とする解、

```prolog
[2,1,3]
[2,3,1]
```

を探索し終えた後、本来は先頭を `3` とする選択へ進むべきである。

しかし実際には、その後に必要となる `perm1` への古い成功継続が失われている。

ログを追跡すると、再帰 `perm1` が失敗した後の処理に問題があることが分かった。

## 成功継続の基本原則

成功継続には二つの性質がある。

1. 直接の次への行き先は、その都度新しく生成する。
2. その直接の成功継続を消費した後は、成功継続スタックに以前から存在する古い成功継続を順番にたどる。

したがって、バックトラックによって再試行するときでも、それ以前に必要だった古い成功継続を破壊してはいけない。

## 発見した問題

再帰 `perm1` の呼び出し前には、例えば次のように成功継続が生成されている。

```text
back_perm1_2_1_0
join_perm1_2_1_0
next_perm1_2_1_1
Spush_next ...
```

この成功継続は、再帰 `perm1` が成功した後に使用するためのものである。

ところが再帰 `perm1` が失敗し、手前の `select1` にバックトラックした後、その `select1` も失敗すると、

```text
back_perm1_2_1_1
join_perm1_2_1_1
end_perm1_2_1_1
Spush_next ...
```

という経路に入り、成功継続が再生成される。

このとき `np` が過去の値に戻ったままだと、次の `Spush_next` が、本来温存されるべき古い成功継続のスロットを再利用して上書きしてしまう。

そのため計算はしばらく正常に進むものの、後になって古い `perm1` への成功継続が必要になった時点で、それが存在しないという症状が現れる。

## 再帰失敗についての考察

再帰呼び出しが完全に失敗した場合、その再帰をもう一度実行しても意味がない。

したがって、

```text
再帰失敗
    ↓
同じ再帰を再試行
```

ではなく、

```text
再帰失敗
    ↓
一つ手前の選択点へバックトラック
    ↓
そこで別の選択肢を試す
```

とするのが自然である。

例えば、

```prolog
perm1(...) :-
    select1(...),
    perm1(...).
```

なら、再帰 `perm1` が完全失敗した場合には、その `perm1` を再試行するのではなく、直前の `select1` のバックトラック地点へ戻る。

## ただし np の扱いに注意

以前にも「再帰失敗時には直前の back へ戻る」という方式を試したことがあり、部分解までは正しく得られていた。

しかし途中で探索が停止した。

今回の解析から、その原因は `np` を更新していなかったことではないかと考えられる。

再帰失敗時には二種類の状態を区別する必要がある。

* 変数状態を復元するための過去の `np`
* 温存すべき成功継続スタックを示す現在の `np`

直前の選択点へバックトラックする際には、変数ポインタや束縛状態を復元するため、一旦その失敗継続に保存された過去の `np` へ戻る必要がある。

しかし、その `np` のまま再試行すると、次の `Spush_next` が古い成功継続を上書きしてしまう。

そこで、再帰失敗時には現在の `np` を保存しておく。

概念的には次の処理とする。

```text
再帰が完全失敗
    ↓
current_np = np を保存
    ↓
再帰バックトラック用フラグ ON
    ↓
直前の back へ移動
    ↓
back に保存された np へ一時的に戻る
    ↓
変数ポインタ・束縛状態を復元
    ↓
フラグが ON なら
    np = current_np
    flag = OFF
    ↓
直前の選択点を再起動
```

つまり、

**制御と変数状態は一つ前へ戻すが、成功継続スタックは現在の状態を温存する。**

## 実装案

再帰失敗時のみ使用する一時的なフラグと `np` 保存領域を設ける。

概念例：

```c
/* recursive call completely failed */

saved_current_np = np[th];
recursive_back_flag = 1;

/* jump to the previous backtracking point */
goto *previous_back;
```

通常のバックトラック処理で、失敗継続に保存されていた `np` を使用して変数状態を復元する。

その直後、

```c
if (recursive_back_flag) {
    np[th] = saved_current_np;
    recursive_back_flag = 0;
}
```

として成功継続スタックの位置だけを元に戻す。

このフラグは再帰失敗から直前のバックトラック地点へ移動する一連の処理の中で直ちに消費されるため、単純な一時フラグで実装できる可能性が高い。

## 設計原則の候補

再帰については次の原則を検討する。

```text
再帰成功
    → 通常の成功継続をたどる

再帰完全失敗
    → その再帰自身を再試行しない
    → 一つ前のバックトラック地点を再起動する
    → 変数状態はその地点まで復元する
    → 成功継続の np は再帰失敗時の現在値を温存する
```

要するに、

> 再帰失敗では「過去の選択状態」は復元するが、「現在まで構築された成功継続」は破壊しない。

これにより、以前の「直前へバックトラックする方式」で発生していた部分解での停止と、現在発生している `perm1` への古い成功継続の上書きの双方を解決できる可能性がある。
