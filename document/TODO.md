
# SCBM 改修計画

## 目的

成功継続について、「生成された成功継続のトップ位置」と「現在実行している成功継続の位置」を分離する。

従来 `np` が両方の役割を持っていたため、成功継続を実行して `np` を減少させると、バックトラック時に必要となる成功継続の生成状態まで失われる。

そこで新たに `ep[th]` を導入する。

`e` は execution を意味する。

## 1. np と ep の役割

`np[th]`

生成された成功継続のトップ位置を保持する。

成功継続を実行しても `np` は減少させない。

`ep[th]`

現在実行する成功継続の位置を保持する。

成功継続を実行するときにのみ減少させる。

したがって、

```text
np = 成功継続の生成・保存位置
ep = 成功継続の実行・復元位置
```

とする。

## 2. 初期化

SCBM開始時には、

```c
np[th] = 0;
rp[th] = 0;
ep[th] = 0;
```

とする。

その後、

```c
Spush_next(&&success, th);
```

によって最初の成功継続を生成する。

## 3. Spush_next

成功継続を生成するときは `np` と `ep` の双方を増加させる。

```c
static inline void Spush_next(void *cont, int th)
{
    if (np[th] + 1 >= RECURSIZE)
        Jerrorcomp(RESOURCE_ERR,
                   Jmakestr("Spush_next SCBM stack size"), NIL);

    np[th]++;
    ep[th]++;

    next_goto[np[th]][th] = cont;
}
```

成功継続の生成位置は `np` によって決定する。

## 4. Spop_next の廃止

従来の

```c
Spop_next(th);
```

は廃止する。

成功継続の実行によって `np` を減少させてはならない。

`np` は生成済み成功継続のトップ位置を保持し続ける。

## 5. Spop_exec の新設

成功継続を実行するときは `ep` のみを減少させる。

```c
static inline void Spop_exec(int th)
{
    if (ep[th] <= 0)
        Jerrorcomp(RESOURCE_ERR,
                   Jmakestr("Spop_exec SCBM stack size"), NIL);

    ep[th]--;
}
```

`np` は変更しない。

## 6. 成功継続の実行

成功継続の実行位置は `np` ではなく `ep` を使用する。

```c
next = next_goto[ep[th]][th];
Spop_exec(th);
goto *next;
```

また、実行すべき成功継続が残っているかどうかの判定も `np` ではなく `ep` を使用する。

従来の

```c
if (np[th] == 0)
```

は、

```c
if (ep[th] == 0)
```

へ変更する。

## 7. 成功継続に保存された変数ポインタの復元

成功継続は単なる制御アドレスだけではない。

成功継続には、その継続を生成した時点の変数ポインタ `vp` も対応している。

したがって成功継続の実行位置を `ep` に変更する場合、変数ポインタの復元も必ず同じ `ep` の位置から行わなければならない。

つまり、

```text
制御継続の取得位置 = ep
変数ポインタの取得位置 = ep
```

でなければならない。

成功継続の実行時に、

```c
next_goto[ep[th]][th]
```

を参照しているにもかかわらず、変数ポインタを `np` の位置から復元してはならない。

それを行うと、

```text
制御       = ep 世代
変数環境   = np 世代
```

となり、異なる世代の成功継続と変数環境を組み合わせることになる。

`fib/2` で発生した `is/2` の未束縛変数は、この不整合によって説明できる可能性がある。

したがって成功継続に関連する以下の情報は、実行時にはすべて同一の `ep` を基準として復元する。

```text
・成功継続アドレス
・変数ポインタ vp
・その他、成功継続と一体として保存している状態
```

一方、それらを新規生成・保存するときの位置は `np` を使用する。

## 8. バックトラック時の処理

失敗継続には、その失敗継続を生成した時点の `np` が保存されている。

バックトラック時には、

```c
np[th] = Sget_np(th);
ep[th] = np[th];
```

とする。

つまり、生成された成功継続のトップ位置を保存時点まで復元し、その位置から成功継続の実行を再開するため `ep` を `np` に同期させる。

これは `success` からの強制バックトラック、`allfail`、`false` など、失敗継続から再開する経路すべてについて適用する。

## 9. allfail

`allfail` では失敗継続を一段戻す。

ここでは成功継続を実行しているわけではないため、

```c
Spop_next(th);
```

を行ってはならない。

失敗継続に保存された `np` を復元し、

```c
np[th] = Sget_np(th);
ep[th] = np[th];
```

とする。

## 10. 基本原則

通常の成功継続生成：

```text
np++
ep++
```

通常の成功継続実行：

```text
ep--
np は変更しない
```

バックトラック：

```text
np = saved_np
ep = np
```

成功継続の保存：

```text
np を使用
```

成功継続の実行・状態復元：

```text
ep を使用
```

## 11. 段階的な実装と検証

一度に全面変更しない。

まず正常動作している従来方式へ戻し、成功継続の意味を壊さないよう段階的に `ep` を導入する。

最初の基準テストには、失敗継続の影響を受けない `fib/2` を使用する。

```prolog
?- fib(10,X).
X = 55.
```

これを成功継続系の基準とする。

`fib/2` が正常動作することを確認した後、

```text
likes/2
select1/3
perm1/2
```

の順でバックトラックを含むテストへ進む。

特に `fib/2` が失敗した場合には、失敗継続側ではなく、

```text
成功継続の実行位置
成功継続に保存された変数ポインタ
np と ep の対応
```

を優先的に調査する。

## 12. 実装漏れ確認

コード全体について以下を検索する。

```text
Spop_next
next_goto[np[th]]
np[th]--
--np[th]
Sget_np
成功継続から vp を復元している箇所
成功継続に付随する状態を np で取得している箇所
```

成功継続の「生成」に使われる `np` と、「実行・復元」に使われる `ep` を明確に分類する。

今回の改修の核心は、

**成功継続そのものの意味は変更せず、成功継続の生成位置と実行位置だけを分離すること**

である。
